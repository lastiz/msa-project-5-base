# ADR-001. Реализация ETL с использованием Spring Batch

## Название задачи

Вынос обработки складских CSV из монолита в отдельный сервис Spring Batch.

### Автор

Дикунов М.А.

## Дата

2026-10-25

## Контекст и проблемы

Монолит принимает файл и сразу обрабатывает строки в запросе пользователя. При росте нагрузки обработка занимает ресурсы ERP и создает много обращений к PostgreSQL. Пользователь ждет завершения, а ошибки сложно искать по разрозненным логам. Перенос БД и файлов в GCP сам по себе эти проблемы не решает.

## Функциональные требования

1. Принимать CSV через существующий интерфейс и сохранять исходный файл в GCS.
2. Проверять строки, дополнять их справочными данными и обновлять остатки и номенклатуру в PostgreSQL.
3. Обрабатывать отчет в фоне, показывать пользователю статус и результат.
4. Повторять временно неуспешные операции и поддерживать перезапуск без дублирования изменений.

## Нефункциональные требования

1. Обрабатывать около 400 000 строк в сутки с ростом нагрузки в два или три раза.
2. Принимать от 100 до 150 параллельных загрузок без блокировки интерфейса длительной обработкой.
3. Целевое среднее время обработки отчета из 2 000 строк составляет до 30 секунд. Ожидание в очереди также нужно учитывать при проверке.
4. Сохранить совместимость с Java, PostgreSQL и GCS. Обеспечить возможность увеличивать число обработчиков.
5. Предусмотреть статусы, логи и метрики для будущего централизованного мониторинга.

## Решение

Выбран Spring Batch. Он подходит для чтения файлов, обработки порциями, транзакционной записи и сохранения состояния выполнения. Это соответствует Java стеку компании и опыту команды. Airflow для одного ETL процесса не нужен, а распределенные вычисления пока избыточны.

Добавляется отдельное приложение Spring Boot со Spring Batch. Монолит на Java 11 и WildFly остается без обновления. Новый сервис запускается в собственном контейнере на Java.

### Порядок работы

1. Монолит проверяет формат загружаемого CSV и сохраняет его в GCS под неизменяемым именем. Затем регистрирует задание в служебной схеме БД номенклатуры с идентификатором отчета, складом и ссылкой на файл. Пользователь получает подтверждение приема, а не сообщение об успешной обработке.
2. Фоновый обработчик забирает ожидающее задание из БД и запускает Spring Batch. Очередь заданий хранится в таблице, отдельный брокер не добавляется. Выбор задания и его закрепление за обработчиком выполняются атомарно, чтобы две реплики не взяли один отчет.
3. Сервис читает CSV из GCS, проверяет строки и обогащает их данными из отдельной БД справочников. Чтение идет последовательно, справочные данные запрашиваются порциями, а не отдельным запросом для каждой строки.
4. Данные записываются в БД номенклатуры порциями, например по 1000 строк, с транзакцией на порцию. Размер порции и число параллельных задач уточняются тестами. Spring Batch сохраняет состояние шагов и точки перезапуска в JobRepository.
5. Монолит читает статус задания и передает результат в Angular через существующие WebSockets. Пользователь видит завершение или ошибку и может исправить отчет.

### Хранение и надежность

Исходные файлы остаются в GCS. Сохраняются две PostgreSQL из исходной архитектуры: БД справочных данных о товарах и БД номенклатуры с остатками. Сервис читает справочники из первой и записывает результат во вторую. В БД номенклатуры добавляется отдельная служебная схема с заданиями и таблицами Spring Batch, третья БД не требуется.

Запись порции и ее состояния выполняется в одной транзакции БД номенклатуры с общим менеджером транзакций. Чтение отдельной БД справочников в эту транзакцию не входит. В части фоновой обработки монолит работает только с таблицей заявок, внутренние таблицы Spring Batch ему не нужны. Существующие обращения монолита к обеим БД сохраняются.

Идентификатор отчета используется как постоянный параметр задания. Повтор запроса не создает новое задание для того же отчета. Запись остатков обновляет значения по ключу склада и товара, а не повторно прибавляет их.

Для временных ошибок БД и сети задаются ограниченные повторы. Ошибочные строки не пропускаются молча, задание останавливается с описанием ошибки. После сбоя процесса требуется обнаружить прерванное выполнение, убедиться, что старый обработчик не работает, и перезапустить его с сохраненного состояния. Это дополнительная логика сервиса, а не автоматическая очередь Spring Batch.

Отчеты одного склада обрабатываются последовательно, разных складов могут выполняться параллельно. Порядок отчетов определяется версией или временем отчета, чтобы поздно загруженный старый файл не перезаписал новые остатки.

### Развертывание

Сервис можно запускать в Docker рядом с монолитом и затем размещать в GCP. Для увеличения нагрузки добавляются реплики с общей БД заданий. Число активных задач и соединений ограничивается возможностями PostgreSQL.

## Альтернативы

| Вариант | Почему не выбран |
| --- | --- |
| Apache Airflow | Удобен для управления несколькими системами, но саму обработку строк и транзакции все равно нужно реализовать отдельно |
| Apache Spark | Подходит для больших распределенных расчетов, но добавляет лишнюю инфраструктуру для текущей обработки файлов |
| Обычное Java приложение | Не требует Spring Batch, но хранение состояния, перезапуск и обработку порциями придется разрабатывать самостоятельно |

## Последствия, ограничения и риски

1. Длительная обработка уходит из запроса пользователя, но появляется отдельный сервис и фоновая очередь в БД.
2. При сбое уже записанные порции остаются в БД. Если требуется публиковать отчет целиком, понадобится промежуточное хранение и отдельный шаг применения результата.
3. Обе PostgreSQL используются монолитом и обработчиками. Увеличение числа обработчиков без ограничения нагрузки может ухудшить работу ERP. Изменение справочников во время обработки может повлиять на результат, если нужен единый срез данных, потребуется фиксировать их версию для отчета.
4. Сохранение файла в GCS и регистрация задания не являются одной транзакцией. Незарегистрированные файлы нужно выявлять и удалять либо повторно регистрировать.

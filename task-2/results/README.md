# Задание 2. Разработка дизайна модуля пакетной обработки данных

## Сравнение решений

Нужно ежедневно в 06:00 формировать CSV с ценами для клиентов. Объем выгрузки составляет от 5 000 до 10 000 строк. Данные хранятся в PostgreSQL, Kubernetes уже используется.

| Критерий | Spring Batch | Apache Airflow | K8s Job / CronJob | Spark |
| --- | --- | --- | --- | --- |
| Расписание CRON | Нужен дополнительный планировщик | Есть встроенное расписание | CronJob запускает Job по расписанию | Нужен внешний планировщик |
| Сложность реализации | Средняя, нужно настроить шаги обработки | Средняя, нужно описать пайплайн | Низкая, достаточно запроса и записи CSV | Высокая для простой выгрузки |
| Ресурсоемкость | Средняя, приложение Java и история запусков | Выше, постоянно работают компоненты Airflow | Низкая, контейнер работает только во время выгрузки | Выше, нужны процессы распределенной обработки |
| Масштабирование | Можно разделять обработку, нужна настройка | Можно добавлять исполнителей, требуется сопровождение | Достаточно одной задачи, разделение по клиентам потребует доработки | Подходит для больших объемов, требует настройки |
| Развертывание в облаке | Нужны контейнер приложения и планировщик | Нужно развернуть отдельную платформу | Просто добавить в существующий Kubernetes | Нужен кластер Spark или облачный сервис |
| Логи и мониторинг | Есть логи и история запусков, метрики подключаются отдельно | Есть интерфейс, статусы и логи задач | Есть статусы задач, сбор логов настраивается отдельно | Есть интерфейс заданий, общий сбор логов настраивается отдельно |

## Решение

Выбран Kubernetes CronJob. Для небольшой выгрузки без сложной обработки достаточно одного приложения по расписанию. Дополнительные возможности Airflow, Spark и Spring Batch здесь не нужны.

Приложение объединяет данные о товарах, категориях, клиентах и индивидуальных ценах. Для каждого клиента создается отдельный CSV в закрытом облачном хранилище. Клиент получает доступ только к своему готовому файлу.

Приложение, PostgreSQL и ELK размещаются в Kubernetes. Логи контейнера собираются в ELK и просматриваются в Kibana. Статусы задач и последний успешный запуск проверяются средствами Kubernetes.

[C4-диаграмма To Be](c4-to-be.puml) показывает систему выгрузки, PostgreSQL, ELK, хранилище и клиента.

## План реализации

1. Согласовать поля CSV и связи таблиц products, categories, clients, client_prices.
2. Написать приложение на Python, которое объединяет таблицы и сохраняет CSV для каждого клиента. Для БД использовать доступ только на чтение.
3. Настроить закрытое хранилище и доступ клиентов к своим файлам. В имя файла включить дату и идентификатор клиента. При повторном запуске заменять тот же файл, публиковать только полностью загруженный результат.
4. Собрать образ Docker. Настройки передавать через конфигурацию Kubernetes, пароли через секреты. Ограничить память и процессор.
5. Настроить CronJob на "0 6 * * *". Запретить одновременные запуски, задать два повтора и ограничить длительность работы. В 06:00 начинается выгрузка, готовые файлы появляются после ее завершения. Возможна задержка запуска контейнера.
6. Настроить сбор логов в ELK. Записывать время запуска, число файлов и строк, результат и ошибки. При ошибке завершать приложение с ненулевым кодом.
7. Проверить запуск вручную и по расписанию, правильность клиентских цен, разграничение доступа и повтор без дубликатов. Измерить длительность.
